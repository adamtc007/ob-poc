## 3. API adaptation (dsl-atoms/dsl-ast catalogue rewrite)

`StructuralKind`/`DeclarativeKind`/`AtomKindClass::Unknown*`/free-function `classify` no longer exist. Every call site now goes through `dsl_atoms::builtin::<CONST>` string constants against `KindCatalogue::builtin()` (or `AtomKindClass::is(KindRole, &str)`), matching the receipt's documented "default-catalogue convenience" — there is no free `classify(&str)` fn in the delivered API (the receipt's acceptance line describes the capability, not a literal symbol name); every adaptation here is `KindCatalogue::builtin().classify(kind)` or the equivalent `AtomBag`/`bag.atoms_of_structural_kind(&str)` call, which is what "default catalogue as a convenience" cashes out to at a call site.

`AtomBag::from_source_file` is now `(SourceFile, &KindCatalogue, &mut DiagnosticBag) -> Result<AtomBag, UnknownKind>`. Adaptation pattern per caller, chosen to preserve each caller's pre-DSL-T1 behaviour exactly:

| caller | pre-T1 behaviour | adaptation |
|---|---|---|
| `dsl-resolution::validator::validate_bpmn` | infallible, unknown kinds silently excluded + diagnosed | `.unwrap_or_default()` — diagnostic already pushed by `from_source_file` before it returns `Err` |
| `dsl-resolution::pack_registry::load_packs_from_dir` | per-file diagnose-and-continue over a directory | `.unwrap_or_default()` per file, loop continues |
| `dsl-semos-frontend::loader::load_verbs_from_dsl_dir` | per-file diagnose-and-continue over a directory | `.unwrap_or_default()` per file, loop continues |
| `dsl-render::renderer::render_dsl` | returns `anyhow::Result<String>` | `?` (blanket `From<UnknownKind> for anyhow::Error` via `thiserror`) |
| `dsl-migrate-verify::verify_dsl_source` | returns a `VerifyResult` struct with a `diagnostics: Vec<String>` field | `match` — `Err` pushes a message and returns the struct's existing `validated: false` shape, same as the adjacent parse/assembly-error branches |
| `dsl-migrate-verify::compile_to_spec` | returns `anyhow::Result<JourneySpec>` | `.map_err(...)?` |
| `bpmn-test-harness::compile_dsl` (test helper) | `assert!` panic on any diagnostic error | `.expect(...)` |
| all 9 direct test call sites | fixtures known to use only built-in kinds | `.expect("all kinds known")` |
| `dsl-resolution::resolve::tests::parse_and_resolve` | same | `.expect("all kinds known")` |

`assembly.rs`'s four `bag.atoms_of_structural_kind(StructuralKind::X)` calls became `bag.atoms_of_structural_kind(builtin::X)`. `resolve.rs`/`validator.rs`/`dsl-render`/`dsl-semos-frontend::loader` swapped `atom.kind_class == AtomKindClass::Declarative(DeclarativeKind::Y)` for `atom.kind_class.is(KindRole::Declarative, builtin::Y)`.

### 4.1 `movement.dsl`: a real DSL-T2 regression, isolated, root-caused, fixed
`dsl-source/verbs/registry/movement.dsl:176` carried `\"value\":10000000.0` inside `three-axis-json`'s escalation threshold — a JSON float literal. DSL-T2's `decimal_text` deserializer rejects float literals by design (money/thresholds must be integer or quoted decimal). This is a **stale generated artifact**, not a design choice: `config/verbs/registry/movement.yaml:95` (the YAML source of truth) already has `value: 10000000` (a plain integer); the `.dsl` file's `.0` suffix is an artefact of the pre-DSL-T2 `f64`-typed field always round-tripping through `serde_json` with a decimal point. Confirmed isolated — grepped every `.dsl` file under `dsl-source/verbs/` for the same escaped-quote float pattern on ANY key; the only other float-suffixed values are `ArgConfig.default` (a field DSL-T2 never touched, ranking-score class, not a predicate). Fixed by editing the one line to `\"value\":10000000` — un-drifting the generated file back to what its own YAML source declares, not a design decision.

## 5. `ExecutionPath` / `EnvelopeHandle` — assessed, not decoupled

Prompt C: "drop its two `ob-poc-types` imports." Assessed and **not done**. Both types are architecturally significant, not generic content:

- `ExecutionPath` (`ob-poc-types/src/execution_path.rs`) is a 4-variant taxonomy specific to ob-poc's own dispatch architecture (`RunbookSequencer`, `DslDirect`, `WorkflowDispatched`, `BusFederated`), feeds a 56-arm exhaustive enforcement matrix in `applicability.rs`, and has a stable single-letter wire encoding consumed by the `OB_POC_CONTROL_PLANE_ENFORCE_VERBS` env-var grammar.
- `EnvelopeHandle` (`ob-poc-types/src/envelope_handle.rs`) is explicitly re-exported (`envelope.rs:81`, with a doc comment saying so) precisely so other ob-poc code's references to `ob_poc_control_plane::envelope::EnvelopeHandle` stay type-identical to `ob_poc_types::EnvelopeHandle`.

Duplicating either locally would fork production enforcement semantics (`ExecutionPath`) or break type-identity for every other caller (`EnvelopeHandle` — a locally-defined duplicate would not be interchangeable with the ob-poc-types original anywhere else it's used). This is a real design decision — either invert the dependency (control-plane defines the taxonomy, ob-poc-types re-exports) or accept the coupling as intentional and correct the recon's "importable after" framing — not a mechanical import drop. Reported, not absorbed.
