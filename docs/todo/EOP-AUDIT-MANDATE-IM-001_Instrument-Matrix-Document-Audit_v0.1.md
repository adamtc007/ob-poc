### §0.1 Headline

Three things, in order of consequence:

1. **The document column carries four incompatible shapes, not two.** EOP-FIND-MANDATE-T0-001
   found two; there are four, and the fourth demonstrates a type that
   **cannot deserialise its own output**.
2. **Every `ACTIVE` trading profile is test residue.** All 16 belong to CBUs named
   `tmm_<hex>_test_cbu`, generated by `rust/tests/trading_matrix_materialize_test.rs:56`.
   No real CBU has ever had an ACTIVE trading profile. This *downgrades* the
   severity of the read-path break and *upgrades* a different finding: the
   configuration layer has essentially never been used in anger.
3. **The sub-custodian network exists and is populated — but is an island.**
   `subcustodian_network` holds 85 real rows across 50 markets. It has **zero
   inbound foreign keys**. Nothing in the settlement chain can reach it.

## Part 1.1 — The document column, precisely

`cbu_trading_profiles.document jsonb NOT NULL` (`migrations/master-schema.sql:9462`).
443 rows. Five distinct top-level key signatures, collapsing to **four
incompatible shapes**. **[V]**

| Shape | n | `is_template` | Top-level keys | Deserialises as |
|---|---|---|---|---|
| **A — tree/AST** | 416 | false | `cbu_id, cbu_name, children, created_at, metadata, status, total_leaf_count, updated_at, version` | `TradingMatrixDocument` ✔ |
| **B — flat + CA** | 16 | false | `booking_rules, constraints, corporate_actions, investment_managers, isda_agreements, metadata, pricing_matrix, settlement_config, standing_instructions, universe, valuation_config` | `TradingProfileDocument` ✔ |
| **C — flat, no CA** | 7 | false | as B, minus `corporate_actions` and `metadata` | `TradingProfileDocument` ✔ (both are `#[serde(default)]`) |
| **D — ad-hoc template** | 3 | true | `components, is_template` | **neither type** ✘ |
| **E — tree, no timestamps** | 1 | true | `cbu_id, cbu_name, children, metadata, status, total_leaf_count, version` | **`TradingMatrixDocument` ✘** — see below |

Status correlation is exact: **all 416 shape-A rows are `DRAFT`; all 16 shape-B
rows are `ACTIVE`; all 7 shape-C rows are `DRAFT`.** **[V]**

### Shape E — a type that cannot read its own output **[V]**

`TradingMatrixDocument` (`rust/crates/ob-poc-types/src/trading_matrix.rs:809-847`)
declares `created_at` and `updated_at` as:

```rust
#[serde(skip_serializing_if = "Option::is_none")]
pub created_at: Option<String>,
#[serde(skip_serializing_if = "Option::is_none")]
pub updated_at: Option<String>,
```

`skip_serializing_if` **without** `#[serde(default)]`. Every other optional field
on the struct carries `#[serde(default)]` — `cbu_id` (`:813`), `cbu_name` (`:817`),
`status` (`:823`), `total_leaf_count` (`:829`), `metadata` (`:832`),
`corporate_actions` (`:846`). These two do not.

`TradingMatrixDocument::new()` (`:866-879`) sets `created_at: None, updated_at: None`
(`:875-876`). The template writer calls exactly that
(`rust/src/domain_ops/trading_profile.rs:1410-1415`) and serialises the result.
The emitted JSON therefore omits both keys — which is precisely the row observed:

```
profile_id 51ec5baa-779a-4066-a0bb-61abe23560ff, created 2026-03-31T11:09:59Z
{"cbu_id": null, "status": "DRAFT", "version": 1, "cbu_name": null,
 "children": [], "metadata": {}, "total_leaf_count": 0}
```

**[I]** Reading this row back as `TradingMatrixDocument` fails with
`missing field 'created_at'`, because serde's derive does not imply `default`
for `Option<T>`. The struct's serialiser can emit a form its deserialiser
rejects. *What would settle it definitively:* a three-line round-trip test —
`from_value(to_value(TradingMatrixDocument::new("","")))`. I did not write one,
because this task forbids writing Rust. The shape of the evidence (attribute
present, `default` absent, `None` at construction, key absent in the stored row)
is verified; only the runtime error string is inferred.

### B1 — `GET /api/cbu/:cbu_id/trading-matrix` returns HTTP 500 for every ACTIVE profile

**Failure [V].** `ast_db::load_active_document`
(`rust/crates/ob-poc-trading-profile/src/ast_db.rs:63-87`) filters
`status = 'ACTIVE'` (`:72`) and parses with
`serde_json::from_value::<TradingMatrixDocument>` (`:82`). Every ACTIVE row is
shape B (flat), which lacks the non-defaulted `version` and `children`. The
route handler maps the parse error to
`StatusCode::INTERNAL_SERVER_ERROR` (`rust/src/api/trading_matrix_routes.rs:75-78`),
**not** to the graceful empty-tree branch at `:66-74`.

**Blast radius [V].** One call site, one route
(`trading_matrix_routes.rs:59`, route registered `:85`). 16 of 2,302 CBUs.
Frontend consumers: `ob-poc-ui-react/src/features/viewport/ViewportPage.tsx:28`, `:323-324`.

**Severity qualifier [V].** All 16 affected CBUs are named `tmm_<hex>_test_cbu`
and are generated by `rust/tests/trading_matrix_materialize_test.rs:56`
(`let prefix = format!("tmm_{}", &Uuid::new_v4().to_string()[..8])`). **No
production CBU is affected, because no production CBU has an ACTIVE trading
profile at all.** The bug is real and the code path is wrong; the current
*impact* is zero. This corrects the framing in EOP-FIND-MANDATE-T0-001 §0.1,
which described 16 profiles as unreadable without establishing whose they were.

and nothing connects the directory to the settlement chain.** This is neither
"already modelled" (→ pure conformance) nor "absent" (→ pure greenfield). It is

### Base currency — where it actually lives **[V]**

### Does the codebase conflate FX with SSI? — **yes, structurally [V]**

1. **Every SSI pins a currency.** `cbu_ssi.cash_currency varchar(3)` (`:9254`),
   under a table comment claiming *"Pure SSI account data. No routing logic"* (`:9276`).
2. **Currency is a *ranking input* to SSI selection.** In the generated
   `specificity_score` (`:18500-18524`), `currency IS NOT NULL` is worth exactly
   **2 points**, below counterparty (32), instrument class (16), security type (8),
   and market (4).
3. **The same key means two different things in one document.**
   `BookingRuleMatch.currency` (`types.rs:447`) = "match this trade's currency";
   `StandingInstruction.currency` (`types.rs:466`) = "this account's currency".
4. **The coverage validator selects currency and then ignores it.**
   `cbu-custody.validate-booking-coverage` (`sem_os_postgres/src/ops/custody.rs:233-247`)
   selects `u.currencies` and reports it (`:281`), but the `NOT EXISTS` join
   matches only on `instrument_class_id` and `market_id` — **never on currency**.

**[I]** The conflation is a consequence of the absence, not a separate defect:
because there is no place for "what currency does this become", the only
currency decision the system makes on the settlement path is "which SSI
applies". *What would settle the design question:* whether auto-FX is intended
to be a property of an account, of a market, or a standalone instruction — the
code expresses no preference because it expresses nothing.

# Part 4 — Structural confusions

## §4.1 Booking-rule ties — a real hole that has **not** manifested **[V]**

`ssi_booking_rules` has UNIQUE on `(cbu_id, priority, rule_name)` (`:27819`) and
`(cbu_id, rule_name)` (`:27827`) — **none on the criteria tuple**. Two rules with
identical criteria and priority would tie, and every resolution path is
`ORDER BY priority ASC, specificity_score DESC LIMIT 1`, which would then pick
arbitrarily.

Grouping by `(cbu, priority, specificity_score)` looks alarming — 9 groups, the
largest with 7 members. **But that is the wrong test:** rules can share a score
and still match disjoint trades. The correct test groups by the actual criteria
tuple:

```sql
SELECT c.name, r.priority, r.instrument_class_id, r.security_type_id, r.market_id,
       r.currency, r.settlement_type, r.counterparty_entity_id, count(*)
FROM "ob-poc".ssi_booking_rules r LEFT JOIN "ob-poc".cbus c ON c.cbu_id=r.cbu_id
WHERE r.is_active GROUP BY 1,2,3,4,5,6,7,8 HAVING count(*) > 1;
-- → 0 rows
```

**No true duplicates exist in live data.** The hole is latent, not active. This
is a correction to the framing in EOP-FIND-MANDATE-T0-001 §B (Law 8), which
described the tie as a live ambiguity; it is a structural permission that has
not been exercised.
